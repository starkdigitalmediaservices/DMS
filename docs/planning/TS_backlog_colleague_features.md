### TS1 — Two-axis table stitching engine (vertical column-merge + horizontal row-merge) — DONE 2026-08-26
The feature the user explicitly asked about. A three-layer decision hierarchy for reconstructing a logical table from OCR'd fragments split across pages: (1) **evidence layer** — read printed column numbers directly off headers where present, zero-cost; (2) **decision layer** — deterministic, unit-tested rules: vertical "continues downward" by fuzzy header-similarity (≥70%, OCR-noise tolerant) or matching column-count with no headers; horizontal "joins sideways" by column-span adjacency against the document's own widest printed column number; (3) **adjudication layer** — narrow, structure-only local-model call for the remaining ambiguous cases, cached per table-*shape* hash (not per document), with a **hard pre-veto**: a join is refused outright when row counts disagree, regardless of what the model says — this is the load-bearing safety property, added after a real regression where the model mislabeled a downward continuation as a sideways split.
Also includes: position-based row pairing via cell bbox y-coordinates for uneven left/right row counts (falls back to strict parity + flag-for-review when no bbox exists).
**Depends on:** T73 (structured-record extraction) as the natural integration point; benefits from TS3 (OCR raw-response caching) existing first so iteration doesn't re-run OCR each time.
**Size:** L — the largest, most novel item here.

**Build note:** adapted rather than ported verbatim — this system extracts against a pre-registered field_schema (T24), so the evidence layer compares which *field names* came back with a value per page (already a real signal: the VLM prompt omits a field's key when it isn't visible on that page) instead of parsing printed column numbers off raw OCR headers, which assumes a document convention we have no reference corpus to confirm (A1). Built: `backend/app/pipeline/table_stitch.py` (the engine — field-set evidence, decide_relation, bbox-containment leftover pairing, LLM adjudication, shape-hash caching), `doc_dg_table_shape_decisions` table + `table_shape_service.py` (the cache), wired into `vlm_extraction.py` two ways: (1) the generic path now stitches consecutive pages vertically before continuation-merge runs — fixes a real, confirmed bug where a continuation row starting a fresh page silently became a disconnected orphan fact; (2) `_extract_spread_facts` (T26) now reconciles uneven left/right row counts by bbox position instead of failing the whole page pair to `_join_mismatch` on any count mismatch. Horizontal merging stays scoped to the explicit "spread" template layout — auto-detecting sideways joins on arbitrary templates was judged too risky (could pair genuinely unrelated pages). Live-verified: 19 pure-engine unit tests, 5 real-DB integration tests exercising the actual wired pipeline functions (cross-page merge, uneven-row reconciliation, adjudication + cache-hit-on-second-occurrence, safe-default-when-adjudication-unavailable), full 145-test suite green (1 unrelated pre-existing Cohere-quota failure), migration applied to the real DB, worker process confirmed clean imports. VLM calls themselves are AsyncMock-injected against a real Postgres DB, not a live Gemini call — same rigor as the pre-existing T26 test pattern this extends, not a new shortcut.

### TS2 — Data-loss audit script — DONE 2026-08-26
Word-level (not block-level) diff verifying every word OCR read is present somewhere downstream. Deliberately word-level because stitching/merging legitimately moves text between blocks — a block-count check would false-positive on correct restructuring.
**Why it matters here specifically:** VeritasDocs has an audit-hash-chain requirement (T63) and a Section 63 evidentiary certificate (T65) — a "nothing OCR read is silently dropped downstream" guarantee is directly on-brand for an evidence system, and there's no equivalent check today.
**Depends on:** none functionally, but most useful once TS1 lands (stitching is exactly the kind of restructuring that could silently drop content).
**Size:** S–M.

**Build note:** independently designed (own tolerance thresholds, own regex, own presence-based set-membership comparison) — not modeled on the colleague project's implementation. Adapted in scope too: this system has no single reconstructed "viewer" document, so the audit compares OCR's per-page text (computed fresh during ingestion, no re-OCR needed) against the chunk content actually stored — chunks are what search results, chat citations, and the click-through viewer all serve from, so that's the effective downstream surface here. T78/T77 (export/report) aren't audited since they're curated structured-field packages, not full-text reconstructions. Built: `backend/app/services/data_loss_audit.py` (word tokenizer with a Devanagari fix — plain `\w` splits words at combining-mark boundaries like matras, a real bug caught during testing — plus a small tolerance for chunker-boundary noise), wired into `worker.py`'s ingestion task (best-effort, never blocks ingestion), two new `doc_dg_documents` columns, and a new "data_loss" dimension + `data_loss_documents` drill category on T76's completeness dashboard. Also ships `backend/scripts/audit_data_loss.py` for spot-checking already-ingested documents — this leg has to re-run OCR since raw OCR text isn't archived anywhere yet (that's TS3), documented as a real cost, not a shortcut. Live-verified: 11 unit tests, plus real end-to-end checks against the running stack — real document upload → real ingestion → real DB audit columns populated; real `GET .../completeness/{folder}` and `.../drill?category=data_loss_documents` API calls returning correct aggregates and per-document detail.

### TS3 — OCR raw-response archival + content-hash caching — DONE 2026-08-26
Archive each page's raw OCR/VLM response to storage keyed by page content-hash. An unchanged page is never re-OCR'd on reprocessing; reconstruction/parsing bugs can be fixed and replayed against the archived raw response for free.
**Depends on:** none.
**Size:** M.

**Build note:** confirmed PaddleOCR/Tesseract/pdfplumber did not already do this — `worker.py` recomputed OCR on every ingestion, and T22's VLM extraction re-called Gemini per page on every run too, with no caching at all. Built two independently-designed (not modeled on the colleague project's implementation) content-addressed archive tables: `doc_dg_ocr_archive` keyed by (file SHA-256, OCR engine) — whole-document granularity rather than literal per-page, since OCR providers process a whole file in one call and this system has no partial per-page re-upload mechanism, so document-level caching delivers the same practical benefit; `doc_dg_vlm_archive` keyed by a hash of (file hash, page number, the exact prompt sent) — prompt-inclusive so a template's field_schema changing, or a spread's left vs right half, naturally gets its own cache entry rather than colliding or serving stale data. Both tables are deliberately NOT tenant-scoped: the OCR/VLM output for given bytes+prompt is a pure function of that input, never of who asked, same as a CDN cache — actual tenant data (Documents/Chunks/Facts) stays exactly as isolated as before. Wired into `worker.py` (OCR) and `vlm_extraction.py` (VLM, both the generic and spread paths) as best-effort — a cache failure just means doing the real call, never a hard failure. Live-verified: 11 unit/integration tests (including a real proof that a cache hit serves the *correct* cached data even when a second, differently-configured mock would have produced different output) plus a real end-to-end check — uploaded the same real Marathi PDF to the real account twice, confirmed via worker logs the second ingestion hit the OCR cache and skipped OCR entirely while still producing correct real chunk content.

### TS4 — Shape-keyed human-answer caching, generalized to the verification workbench — DONE 2026-08-26
The general pattern behind TS1's reviewer-decision cache ("ask once per *kind* of ambiguity, apply to every future instance of that shape") applied beyond table stitching to other HITL review flows already in the verification workbench. Reduces reviewer repeat-work as more documents of a known form/layout are ingested.
**Depends on:** TS1 (reuses/extends its shape-hash caching mechanism rather than building a second one).
**Size:** M.

**Build note:** two parts. (1) Closed a real gap TS1 left open — `doc_dg_table_shape_decisions` supported `decided_by='human'` from day one, but no code path ever let a human set it: `_stitch_vertical_segments` silently defaulted ambiguous, non-adjudicated pairs to "not stitched" with nothing surfaced for review. Now writes a `_stitch_ambiguous` Fact (deduplicated per shape_hash so a batch of documents sharing one ambiguous layout doesn't flood the queue before the first is resolved), a new `stitch_ambiguous` adjudication-queue category, and `POST /facts/{fact_id}/resolve-stitch-ambiguity` — a human's answer is written with `decided_by='human'`, which TS1's existing precedence rule already treats as permanently outranking any future LLM guess for that shape. (2) Generalized to a second, genuinely different HITL flow — the `low_confidence` fact-verification queue — via `doc_dg_field_trust_signal`, tracking how often a given field_name's low-confidence readings have been confirmed correct vs corrected as wrong, surfaced as a `trust_signal` hint per queue item. Deliberately informational only, never auto-promoting: T55's hard rule ("no promotion to verified without an actor event") stays fully intact, a real human still confirms every fact via the existing `confirm_fact`/`bulk_confirm_facts` endpoints — this only gives the reviewer accumulated context, not a bypass. Live-verified: 39 new/updated tests, plus a real end-to-end check against the real account — inserted a real `_stitch_ambiguous` fact, resolved it through the real `resolve-stitch-ambiguity` API, confirmed the shape decision was written with `decided_by='human'` correctly attributed to the real actor, and confirmed the item dropped out of the queue once resolved.

### TS5 — Ditto-chain forward-fill with explicit break rules — DONE 2026-08-26
Store both the literal OCR reading (`verbatim`, e.g. "Do.") and a resolved/forward-filled value per cell, with a `was_ditto_filled` flag. Forward-fill is explicitly refused (and flagged for review instead) across a village change, a table restart, or a broken source chain.
**Needs verification first:** confirm our actual Marathi/Devanagari waqf registers use the same "Do."-style ditto convention before committing effort — this is a scoped, concrete win only if the source documents match.
**Depends on:** none functionally; sequence after TS1 since both touch cell-level table structure.
**Size:** M.

**Build note:** verification came for free — the real 1973 Maharashtra Waqf Board gazette table used for TS1's real-data test already showed this exact "Do." convention repeatedly (rows 181-197 all read "Do." under Sunni/Object/Mutawalli). That real data also caught a real, pre-existing bug: the ditto-mark matcher (T27, already built) only matched the bare lowercase `"do"` exactly — it would never have recognized the real register's actual "Do." (capitalized, trailing period), silently leaving every ditto row unresolved. Fixed with a case/period-normalizing match. Added `verbatim`/`was_ditto_filled` to each ditto-filled Fact's JSONB value (no migration needed, extends the existing shape), and replaced the handler's old hard-raise-on-broken-chain with a per-cell `_unresolved_ditto_columns` flag that forces the affected Fact to `in_review` regardless of confidence, rather than losing the whole segment's ditto resolution over one broken cell. The "village change" break rule is built as an opt-in `chain_anchor` field-schema role, deliberately NOT auto-inferred from any column name: the existing, already-validated T27 test case shows a real scenario (the same owner holding land in two villages) where blanket-resetting every column on a village change would have been wrong — it only fires when a template explicitly declares which column plays that role, and no currently-registered template does. "Table restart" is already handled for free by TS1's own segment boundaries (ditto expansion never spans across a stitched-table boundary). Live-verified: 18 new/updated tests, plus a real end-to-end re-run of the actual gazette page through the real Gemini pipeline — all 18 real rows resolved correctly (serial 180's literal values, serials 181-197 all correctly forward-filled with the real "Do." mark preserved in `verbatim`).

### TS6 — Page-furniture detection by position-stability — DONE 2026-08-26
Flag (never delete) repeated running headers/footers by checking they sit at a stable vertical position across pages (spread < 5% of page height, within the top/bottom 12% margin) rather than by content-repetition alone. Repetition-only filtering has a documented failure mode (deleted 25% of a 100-page file where legitimate content — a repeated cause-title — was mistaken for furniture).
**Depends on:** none. Relevant only if/where our ingestion pipeline currently does any repeated-content suppression — confirm first.
**Size:** S.

**Build note:** confirmed first, per the item's own prerequisite — no repeated-content suppression exists anywhere in this codebase (searched the full pipeline/OCR/worker/services tree). User explicitly chose to build it from scratch as new infrastructure rather than skip. Adapted, independently designed: no OCR provider in this pipeline (pdfplumber/tesseract/paddleocr) persists per-line pixel bounding boxes past extraction, so position is approximated by a line's order within its own page's line sequence (top/bottom margin by line index) rather than a literal Y-coordinate — a real, available signal, not a guess. Own thresholds (margin, spread, min-occurrences), not copied from any reference. Built `app/services/page_furniture_service.py` (pure detection function, flags only, never deletes/filters anything), wired into `worker.py` alongside TS2's audit, a new nullable `doc_dg_documents.page_furniture_candidates` column, and a T76 completeness-dashboard dimension + drill category, matching TS2's exact integration pattern. Live-verified against the real 13-page waqf case file with real PaddleOCR: caught and fixed a real bug along the way — a ditto mark ("Do.") repeating many times as separate lines *within one page* was being counted as 13 "occurrences" and wrongly flagged as furniture; fixed by deduplicating to at most one occurrence per page, so occurrence_count now genuinely means distinct pages. After the fix, the real document correctly produced zero false positives — and honestly, zero true positives either, since this particular document is a heterogeneous compiled case file (form, letter, order, gazette excerpt) whose OCR'd page-tops each differ slightly, not a long uniform register with a byte-identical repeated masthead (the scenario this feature actually targets). 10 unit tests, full regression suite green, real API check confirms the dashboard wiring.

### TS7 — Cross-script glossary-first search expansion — DONE 2026-08-26
Hand-curated EN/Devanagari synonym table for domain vocabulary (waqf/wakf/वक्फ, kabrastan/qabrastan/graveyard/कब्रस्तान, etc.), checked first and free; only unseen terms fall through to a cached translation call. Complements existing T72 (pg_trgm fuzzy match) and BGE/Cohere reranking rather than replacing either.
**Depends on:** none.
**Size:** S.

**Build note:** adapted to what this system actually already has — a real LLM-based trilingual query expansion (`_expand_trilingual_query`) already runs on *every* search unconditionally, so "only unseen terms fall through to a paid call" doesn't apply as literally stated; the glossary's genuine value here is different and arguably stronger: that LLM call silently degrades to echoing the raw query verbatim on any failure, including air-gapped mode with no local LLM (T92's `enforce_local` gate), so cross-script recall would otherwise vanish entirely in that case. The glossary is a free, local, always-available fallback that fills exactly that gap, and guarantees the exact indexed term for known vocabulary rather than trusting a general-purpose model's translation. Scoped to the embedding leg of search only (`tri_queries`) — search already runs each query variant as an independent vector search and RRF-merges, so adding more is purely additive; deliberately NOT folded into the keyword-search legs, which AND their terms together via `plainto_tsquery` (concatenating extra words there would make search *more* restrictive, the opposite of expansion). Built `sys_dg_search_glossary` (16 synonym groups, 53 terms) following the `sys_dg_translations` (T95) table-shape convention per the codebase's own precedent, seeded from terms directly observed in the real waqf-register documents processed this session (mutawalli, gunthas, mouje, etc.) — independently curated, not copied from any reference. 8 unit tests. Live-verified end to end against the real account: uploaded the real 1973 gazette document, confirmed genuine "वक्फ" Devanagari content is present, then ran a real search API call for the English-only query "wakf mandal address" with `AIR_GAPPED=true` (LLM expansion forced unavailable) — the real Devanagari chunk came back as the top-ranked result, proving the glossary path works exactly as designed even when the LLM path can't.

### TS8 — OCR engine comparison / bake-off harness — DONE 2026-08-27
Structured head-to-head scoring of OCR engines on table-row capture, cell-bbox coverage, and a "degenerate table" detector (>90% empty cells = not a real table). Since T90 already gives us Tesseract/pdfplumber/llamaparse/PaddleOCR as interchangeable providers, this would inform provider defaults per document type/language instead of one hardcoded default.
**Depends on:** T90 (already done).
**Size:** M.

**Build note:** adapted, per the item's own logic, once the real engine interfaces were checked: none of the three local engines (pdfplumber's native text layer, Tesseract, PaddleOCR — LlamaParse excluded from this pass, user chose local-only rather than uploading the real document to that cloud API) produce real table-cell/row structure, and there's no labeled ground-truth corpus for this project's real registers (A1, same constraint already blocking T25/T31/T32) to score row-count precision/recall against. Built ground-truth-free proxies instead: how much of the page was actually read (char/line volume), a Devanagari-script capture ratio (this product's stated priority script), a row-likeness heuristic shaped for this project's own numeric multi-column gazette tables, and the literal >90%-empty-pseudo-cell degenerate-table detector from the item as written. A real, confirmed finding made while building this: PaddleOCR's `predict()` already returns `rec_boxes` (a bbox per detected line) and Tesseract's `image_to_data()` already returns a bbox per word, but neither is captured anywhere in the existing pipeline — `extractor.py` only ever reads `rec_texts` / calls `image_to_string()`, discarding position data both libraries already compute; wiring that into real Facts would be its own feature (T06 fact-regions already exist for VLM output), out of scope here. Built `backend/app/services/ocr_bakeoff_service.py` (scoring + three engine-runner functions, calling pytesseract/PaddleOCR's structured APIs directly rather than through the existing (buggy, see TS6/TS7 notes) provider-selection routing, so each engine is scored on what it actually produced, not what the routing bug would have silently swallowed) and `backend/scripts/ocr_bakeoff.py` (CLI, same convention as TS2's `audit_data_loss.py`). The recommendation output is decision support only, never auto-applied to `AI_OCR_PROVIDER` — same standing-config-needs-a-human posture as D-4. 10 unit tests, full 219-test suite green. Live-verified against the real `biznesskd07@gmail.com` account: ran the harness against the real 1973 gazette test document already on that tenant — results independently corroborated the pre-existing pdfplumber-priority bug found during TS6/TS7 (pdfplumber's native layer returned a non-empty but info-poor 1355 chars/0 row-like lines/0% Devanagari on a genuinely scanned page, while Tesseract and PaddleOCR both read substantially more real content, Tesseract catching real Devanagari characters) — real independent evidence for a bug already on record, not a new claim taken on faith.
